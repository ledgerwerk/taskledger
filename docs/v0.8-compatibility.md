# v0.8 Compatibility and Removal Matrix

This document freezes the 0.7.8 baseline and classifies the v0.8 cleanup contract before removals begin. The normative implementation scope is `taskledger_v0.8.0_cleanup_plan.md`. Any change to a frozen surface must update this matrix and its contract test in the work package that intentionally changes it.

## PRESERVE

The following are product and data contracts, not cleanup candidates:

- The lifecycle `task -> plan -> approval -> implementation -> validation -> done`, explicit user-only plan approval and criterion waivers, required question/todo/acceptance-criterion gates, and stage/run/lock consistency.
- Validation workspace snapshot checks, stale-lock diagnostics and explicit recovery, append-only audit/event behavior where configured, atomic writes, and corruption-resistant persistence.
- Opaque external references, UUID-backed durable task identity, rebuildable indexes, and canonical Ledgercore project and mount resolution.
- JSON success and error envelope structure and deterministic exit behavior. Preserve `ok`, `command`, `result`, `events`, `warnings`, `result_type` when present, and structured error fields including stable code and exit code. Existing CLI tests assert the success envelope and ensure the process exit code matches the structured error.
- Supported APIs and CLI behavior selected for v0.8. Every intentional public break must be classified, documented, and covered by replacement-contract tests.
- Backup, fingerprints, journal state, idempotency, conflict detection, identity verification, path traversal protections, and independent post-migration verification.
- The latest supported 0.7 durable state must remain migratable. Indexes remain caches and must be rebuilt from canonical records rather than treated as authority.

## BREAK IN 0.8

The following private or explicitly selected compatibility surfaces may be removed or changed after replacement behavior is covered:

- Delete `taskledger.services.tasks`; no production caller may import it. Redirect APIs, CLI callers, and service tests to the owning focused modules.
- Remove private `_v2` naming for current internals, stale aliases such as `ensure_v2_layout`, and compatibility properties used only by current Python callers. Durable `file_version` and schema values remain governed by migration, not renaming.
- Delete `taskledger/cli_misc.py`, unused private ID helpers, duplicate `TaskVisibility`, and pure re-export modules where they have no declared public role.
- Make API exports explicit and deliberately selected. The baseline is 156 names across 15 modules; update the frozen hash only with a reviewed v0.8 API decision and replacement imports/tests.
- Keep `plan accept` as the single normal approval command and remove the duplicate `plan approve` surface. Consolidate migration operations under `migrate`; retain `storage` for current storage inspection/configuration.
- Classify every command as KEEP, REMOVE, MERGE, or MOVE. The preferred source-plan decisions are to remove or extract the four beta source-intelligence commands, minimize release-boundary integration, and keep worker-pipeline and Git-sync features only with clear current ownership and runtime value. Do not retain aliases solely because they existed in 0.7.
- Remove project configuration keys with no runtime consumer, after auditing semantic usage and providing clear migration diagnostics for old keys.
- Break private import cycles and remove unneeded function-scope imports. Retain a nested import only for a concrete lazy-loading or optional-dependency reason recorded in the architecture allowlist, never to avoid a cycle.

## MIGRATE ONCE

Old durable layout knowledge belongs in explicit migration code, not transparent normal runtime behavior:

- Legacy `.taskledger/` and root `taskledger.toml` state is an input to migration. Normal project operations must require canonical Ledgercore registration and mounts and must not silently fall back to legacy paths.
- Preserve upgrade of the latest supported 0.7 state, including legacy task directories and UUID allocation, old root configuration, task/todo/criterion field aliases, indexes, locks, runs, and migration journals. Normalize old durable fields during the migration and make current readers strict where safe.
- Legacy layouts require an explicit plan/apply flow, reviewed conflicts, backups, journals, and post-migration verification. Interrupted work must be recoverable; ambiguous or conflicting ownership must fail safely without losing source data.
- Old indexes may be discarded/rebuilt only as derived caches. Never infer authoritative task identity from display IDs, stale indexes, or directory names alone.
- Do not rewrite schema numbers or relabel existing serialized `file_version` values without an explicit migration and fixtures proving both the accepted source formats and canonical output.

## Baseline command and API freeze

The command and API hashes above are enforced by `tests/test_compatibility_baseline.py`. Update those expected values only when the corresponding work package deliberately changes the inventory. The JSON contract remains covered by `tests/test_json_contracts.py`; do not update its assertions merely to make refactored output pass.

The command inventory source is `taskledger/command_inventory.py`. The API export source is each `taskledger.api.*` module's `__all__`, with the public module list in `taskledger/api/__init__.py`. Existing command registration, API parity, and docs/skill tests remain part of the release contract.
